# 前端适配更新指南（CONTRACT 3.6.0，v2 已合入 main）

> 读者：`apps/web` 的前端开发。范围：`dev/v2` 合入 `main` 后（merge commit `02a3318`）相对上一版 main（3.5.0）新增的所有对外面。
> 结论先行：**v1 的 `/turns` 流完全没变，老的对话 UI 不会坏**；新增的是「群聊会话」与「微信私信」两块能力，前端按需接入，未接入不影响现有功能。

## 1. 契约速查

| 项 | 值 | 说明 |
|---|---|---|
| `CONTRACT_VERSION` | **3.6.0** | minor：新增第 13 个 op `msg.send` + 微信/八卦；v1 的 12 个 op 语义不变 |
| `API_VERSION` | **3** | 模块 manifest 的 `apiVersion` 必须是 3（旧的 2 会被引擎拒绝加载，见后端指南） |
| `SCHEMA_VERSION` | 2 | 存档 schema 不变 |
| 提示词版本 | `CONVERSATION_PROMPT_VERSION 2026-11-19.2` / `GOSSIP_PROMPT_VERSION 2026-11-19.1` | v1 的 `PROMPT_VERSION 2026-11-18.1` 仍然有效，三条线互不覆盖 |
| 错误码 | 39 个 | 前端按 `{ ok:false, code, message }` 处理；`E_AUDIT_UNAVAILABLE` / `E_CONTENT_BLOCKED` 会出现在微信发送里 |

## 2. 新增 / 变更的 HTTP 面

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/rooms/:roomId/messages?actorId=<id>` | 拉某个 actor 的微信收件箱；`actorId` **必填**，且必须是服务端签发的本人 `plr_*`；越权 → 403 |
| `POST` | `/api/v1/rooms/:roomId/messages` | 玩家发微信：body `{ from, to, content }`；成功 `{ ok:true, events: GossipEvent[] }` |
| `GET` | `/api/v1/rooms/:roomId/messages/stream?actorId=<id>` | SSE，事件名 `gossip.message`（只推自己是收发方的消息）；15s 一次 ping |
| `GET` | `/api/v1/rooms/:roomId/events?actorId=<id>` | **行为变更（breaking）**：`msg.sent` 只对收发双方可见；传别人的 `actorId` 现在 **403**（以前是静默过滤） |

要点：

- `actorId` **不得前端自己拼/猜**，一律用建房时服务端返回的 `plr_*`。
- `/events` 不传 `actorId` 时 `msg.sent` 会被过滤掉（静默少数据），所以**要渲染私信必须传本人 actorId**；收到 403 说明传错了 actorId，不要当成网络错误重试。
- `/turns`、`/state`、`/history`、`/gallery` 等老端点无变化。

## 3. 群聊会话（`conversation.*`）渲染规则

服务端产出一串 `ConversationEvent`（`docs/03` 未收录前以 `packages/shared/src/contract/v2.ts` 为准）：

| 事件 | 前端要做的事 |
|---|---|
| `conversation.opened` | 初始化会话视图（参与者列表） |
| `conversation.utterance` | 渲染一条 `Delivery`：**只渲染 `channels` 里列出的部分**（`content`/`action`/`notice`）；缺失字段不要拿原文兜底 |
| `conversation.mental` | 心理活动仅当 `actorId === 自己` 时展示（`secret` 记忆由服务端控制，前端不得请求他人 mental） |
| `conversation.scene` | 场景总结按 `beat.order` 插到玩家发言之前（`before`）或之后（`after`） |
| `conversation.phase` | `listening` = 玩家点了插话、等他说；展示输入框焦点态；服务端会在 `listenTimeoutMs`（默认 30s）后自动恢复 `speaking` |
| `conversation.notice` | 系统提示（如「这句话是对 X 说的」「内容被审核拦截」），样式与正文区分 |
| `conversation.committed` | **只有收到它才更新权威状态**（`state` + `proposals`），并根据 `turn` 推进轮次 |
| `conversation.error` | `code` + `message`；`retryable:true` 时给「重试」按钮 |

三通道表现建议：

- `content`：正常对话气泡；`action`：动作描写（旁白样式）；`notice`：灰色系统行。
- 私密模式（`whisper`/`signal`）对非目标只给 `action`，不要推测内容；`signal` 不携带 content。
- 一个 `utterance.id` 可能拆成多条 `Delivery`（不同人收到的通道不同），按 `utteranceId` 归组渲染，不要按条重复计数。

> 现状：服务端**尚未**把 `ConversationHostV2` 挂到 HTTP/SSE（群聊目前仍走 `/turns` 的 v1 流）。前端接入前先 feature detect（比如探一个 `GET /api/v1/rooms/:id/conversation`，未来加），没探到就退回 v1 渲染。

## 4. 微信 UI

- 收件箱：`GET /messages` 返回 `MessageRecord[]`（`from/to/kind/content/rootId/replyTo/hop/confidence/createdAt/seq`）。
- 实时：订阅 `/messages/stream`，事件 `gossip.message`，**按 `message.id` 去重**（SSE 断线重连可能重放）。
- 发送：`POST /messages`，成功后本地先乐观插入也可，但以服务端返回的 `events` 为准。
- **发送按钮必须前端防抖**：服务端对玩家发信**没有** min-interval 节流（`TalkBudget` 只节流 NPC 自主发言），连点会真的产生多条消息。
- `kind` 渲染建议：`player` 普通、`gossip` 八卦（可显 `hop` 层数）、`reply` 回复、`system` 系统。
- `confidence` 是 0~1 的传播可信度，属可展示的「八卦靠谱程度」；`hop` 是转发层数。
- 私信只给收发双方：不要做「查看全部聊天」的入口，服务端已经过滤。

## 5. 红线

1. 不缓存权威状态：`state` 只从 `conversation.committed` / `/state` 拿。
2. `private`/`secret` 内容不渲染给非目标；前端不请求他人 `actorId` 的收件箱。
3. 不自己拼 `actorId`、不把 `actorId` 当查询参数随意透传。
4. 审核拦截（`E_CONTENT_BLOCKED` / `conversation.error`）不要静默吞掉，给玩家可见提示。
5. 老房间没有 v2 数据（无会话、无消息）时按空态处理，不要报错。

## 6. 验收清单

- [ ] `/turns` 老流程回归通过（不因本次合入变化）
- [ ] `GET /messages` 只返回本人收件箱；传别人 actorId 得到 403 且不当网络错误重试
- [ ] `/messages/stream` 断线重连后按 `message.id` 去重
- [ ] 发送按钮有防抖；连点不会产生多条
- [ ] `/events?actorId=` 不传时私信不渲染，传错 actorId 时 403 有降级提示
- [ ] 群聊三通道（content/action/notice）与私密模式渲染正确，未接入时自动退回 v1
- [ ] `conversation.phase=listening` 有超时兜底（服务端 30s 自动恢复，前端也要清等待态）
