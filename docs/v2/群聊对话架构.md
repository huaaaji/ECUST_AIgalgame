## 1. 核心模型：说话 = 四段结构 + 投递矩阵

### 1.1 Utterance（一句话）

```
Utterance {
  id, speaker, target?, mode,
  content?,        // 话的内容
  action?,         // 完整动作（目标/公开视角，含意义）
  coverAction?,    // 低信息动作（非目标视角；缺省由 mode.actionVocab 生成）
  notice?          // 可选元数据
}
```

四段对应玩家原始需求：说话目标=`target`、说话类型=`mode`、附加行动=`action`/`coverAction`、说话内容=`content`。

### 1.2 三通道（可独立投递）

- `content` —— 话的内容
- `action` —— 动作/神色（对 target 用 `action`，对 others 用 `coverAction`）
- `notice` —— 元数据（如"这句话是对 X 说的"）

**现有 `Envelope.audience` 只表达"看不看得见"，新层表达"看见哪一部分"**，两者叠加：先 audience 过滤谁能收，再 channels 决定收什么。

### 1.3 投递矩阵（数据驱动，写在 `content/v2/utterance-modes.json`）

| mode | target 收到 | 非 target 收到（含玩家） | requiresAction |
|---|---|---|---|
| `broadcast`（不 @） | content + action | content + action（全员皆 target） | 否 |
| `addressed`（@，不悄悄话） | content + action | content + action + notice「对 X 说」 | 否 |
| `whisper`（@ + 悄悄话） | **仅 content** | **仅 action**（coverAction，如「凑近压低声音」） | 是 |
| `signal`（@ + 不动声色） | **仅 action**（有意义的眼色/手势） | **仅 action**（coverAction，如「目光扫过桌面」——无意义） | 是 |

模式定义字段：`id / label / targetChannels / otherChannels / requiresAction / actionVocab / addressedNotice`。
引擎只有一个通用解释器 `deliver()` 按字段投递；**加模式 = 加一条数据**（保 I3）。

### 1.4 检验规则（Arbiter 之前，纯函数）

- `requiresAction` 为真但 `action` 为空 → 拒绝（复用现有 `E_SCHEMA_INVALID`，不新增错误码）；coverAction 缺失按 vocab 补齐。
- `whisper`/`signal` 必须有 `target`，且 target 在场（复用 `scene.presentIds` 唯一真源）。
- `signal` 不允许 `content`（信息密度限制）；有 content 则丢弃该字段并留 fact。
- 所有文本字段长度上限（content ≤ 400、action/coverAction/notice ≤ 120、thought ≤ 300、plan ≤ 200）。

## 2. 心理活动（NPC 的内心）

```
MentalActivity { actorId, thought, plan?, salience:1..5, about?: ActorId[] }
```

- **每轮每个 NPC 都生成一次**（收到消息后，与"是否说话"独立决策）。
- `thought` = 模拟模型的思考：必须有因果逻辑（"因为 A，所以我觉得 B"）和世界相关性（引用在场的人/刚发生的事/自己的记忆），不是随机情绪词。
- `plan` = 允许包含行动计划（用户拍板），但**不自动执行**；它只是 secret 记忆，下一轮该 NPC 的 LLM 看到后可以自行决定要不要落实成 Proposal（仍走 Arbiter，I1 不破）。
- 写入通道：`memory.write`（owner=自己、visibility=secret、tags=["mental"]、about 含相关人），信封 type=`dialogue.speak`（trustedOrigin 含 dialogue，允许代写 secret；`dialogue.think` 只是 Proposal 的 by）。
- 注入：secret + about 命中当前说话人 → forced 注入、不打分、不占预算；低 salience 的只进记忆。
- 玩家**永远看不到**心理活动；玩家能读到的是 `action` 通道。

## 3. 场景 agent（半常驻特权注入）

- 特殊参与者 `actorId="scene_agent"`，不是 NPC，不参与"谁说话"的调度。
- **开场**：会话打开时产出 1 条 SceneBeat（场景描述），向全体广播一次，然后下线。
- **唤醒条件**（用户拍板）：① 玩家显式 @所有人 或 @≥2 人；② 换地点（`move.to`/`scene.set` 改变 locId）。
- **唤醒产物**：一条 `SceneSummary`（群像场景描述），写入会话级 `SceneMemory`：`origin="scene"`、`forced`、按 id 排序、放在 S1.5 世界记忆段之后。旧的 summary 被取代（只保留最新一条）。
- **顺序语义**：场景输出排在玩家发言之后 → NPC 优先对玩家反应；场景输出在玩家发言之前（换地点）→ NPC 按心理和背景自由发挥。
- NPC 的提示词**没有系统级场景段**（S5 删除）；场景信息只通过 SceneBeat / SceneMemory / 收到的交付内容进入其上下文。

## 4. 会话与调度（每个 NPC 独立的 LLM）

### 4.1 ConversationSessionV2（新类型，不改原 DialogueSession）

```
{ id, roomId, participants, phase:"speaking"|"listening", turn, status,
  speaking?, queue: Utterance[], injected: Utterance[],
  sceneBeats: SceneBeat[], sceneMemory?: SceneMemory,
  npcSpeechStreak: number,   // 玩家不发话时连续 NPC 发言数
  visibility }
```

### 4.2 插话（phase 语义）

- 玩家点插话 → `phase="listening"`：当前发言者说完这一句后，其他 NPC **只接收信息 + 生成心理活动，不说话**。
- 玩家的插话进 `injected` 队列；玩家发言结算完成后 `phase` 回到 `speaking`。
- 原 `DialogueHost.interject` 是"立即推进一轮"，语义不同 —— v2 不复用，另起接口。
- `listen` 必须有超时/兜底：玩家点了插话却一直不说话 → 到 `listenTimeout` 自动恢复 `speaking`（否则 NPC 永久沉默）。

### 4.3 自主续聊与长对话惩罚

- 玩家不说话时，会话可以继续：每个在场 NPC 每轮各自一次 LLM，输出 `speak | think | silent`。
- 玩家在场且 `npcSpeechStreak ≥ policy.npcHardCap`（默认 6）→ NPC 本轮**只 think 不 speak**，直到玩家发言或会话被显式关闭。
- 软惩罚：`npcSpeechStreak` 越大，NPC 提示词的 framing 越强（"玩家在旁，闲聊已持续 N 轮，除非有重要信息否则保持沉默"），silent 概率上升。
- 玩家不在场（纯 NPC 会话）→ 不受 hardCap 限制，可以一直聊到 `maxTurns`（默认 40）。

### 4.4 每轮时序

```
玩家 utterance（或空闲 tick）
  → 场景唤醒判断（@多人 / 换地点）
  → deliver(player utterance) 按矩阵算各人通道
  → 对每个在场 NPC（并行、各自独立上下文）：
       一次 LLM → speak/think/silent
       输出全部文本字段送审核
  → 通过的 utterance 直接投递；think 写 secret 记忆（queue 字段尚未启用）
  → [若 phase=listening：只结算当前发言者，其余跳过]
  → 每轮发言合并成一批 Proposal 交 Arbiter（当前只有 memory.write；`npc.spoke` 是有意保留的领域事件，v2 尚未生成，见 §10 偏差）
  → 若场景被唤醒：产出 SceneSummary（排在玩家发言之后 → NPC 优先反应）
  → 发 ConversationEvent：各接收方只看到自己的通道
  → 更新 npcSpeechStreak / phase
```

## 5. 审核扩面（不改现有 AuditGate）

`ConversationAudit.audit(actorId, texts[])`：把 utterance 的 `content`/`action`/`coverAction`/`notice` + MentalActivity 的 `thought`/`plan` 拼成带标签的待审文本，调用同一个 `AuditPort.review`。
- 违规且说话者是玩家 → 复用 `AuditGate.punish`（警告/扣分/删档线，策略仍来自 policy.json）。
- 违规且说话者是 NPC → 丢弃该 utterance/mental，不惩罚玩家。
- 审核器故障 → 全部丢弃（fail-closed），不发布任何新通道文本。

## 6. 事件（新 union，不改原 TurnEvent）

```
ConversationEvent =
  | conversation.opened
  | conversation.utterance   // 只含接收方自己的通道（前端按它渲染）
  | conversation.mental      // 仅供调试/审记，不投递给玩家
  | conversation.scene       // 开场广播 / 唤醒总结
  | conversation.phase       // speaking → listening → speaking
  | conversation.committed   // 本轮的 Arbiter 结果摘要
  | conversation.error
```

`conversation.utterance` 的 payload 直接是 `Delivery`（`to` + `channels` + 各通道文本），前端不需要知道模式定义。
