# dev/v2 前端开发注意事项（给前端同学）

> 适用分支：`dev/v2`。这份文档只讲**前端要接什么、不能做什么**。引擎内部（Arbiter / 投影 / 预算 / 导演）已经封好，前端不要碰，也不要试图在浏览器里复刻规则。
> **行为变更（breaking，dev/v2）**：`GET /events` 携带不属于当前账号的 `actorId` 现在返回 **403**（此前是 200 + 空/越权数据）；前端必须始终传当前登录玩家的 `actorId`，不要传 NPC 或其他玩家的角色 id，否则历史事件会整页失败。
> 本文对应契约：`CONTRACT_VERSION 3.6.0`、`API_VERSION 3`、`GOSSIP_PROMPT_VERSION 2026-11-19.1` / `CONVERSATION_PROMPT_VERSION 2026-11-19.2`。

## 0. 三句必背

1. **前端是只读视图 + 意图发送器**，不是世界状态的第二个权威副本。权威状态只在服务端事件日志里。
2. **玩家不是收件人的微信，前端拿不到、也不该猜**。没有"神色降级"渲染，服务端在 Transport 前已经按 `audience` 过滤。
3. **消息只有「目标 + 内容」**。没有 action、notice、coverAction、channels；看到这些字段就是契约漂移，立刻报后端，不要兼容渲染。

## 1. 新增 HTTP 端点

| 端点 | 用途 | 请求 | 响应 |
|---|---|---|---|
| `GET /api/v1/rooms/:roomId/messages?actorId=<id>` | 拉收件箱（历史消息） | — | `{ ok:true, messages: MessageDigest[] }` |
| `GET /api/v1/rooms/:roomId/events?actorId=<你的角色>&fromSeq=0` | 历史事件（含私信） | `actorId` 必须是当前账号在本房间的玩家角色，否则 403；`msg.sent` 只返回 audience 内含该角色的事件；不带 actorId 时不返回任何私信 |
| `POST /api/v1/rooms/:roomId/messages` | 玩家给 NPC 发微信 | `{ from, to, content, userId? }` | `{ ok:true, events: GossipEvent[] }` 或 `{ ok:false, code, message }` |
| `GET /api/v1/rooms/:roomId/messages/stream?actorId=<id>` | SSE 实时私信 | — | `gossip.message` 事件流 |

**微信与行动额度的边界（有意设计）**：`POST /messages` 不消耗 `TurnLedger` 的「行动额度」（当前服务端没有独立的「回合限流器」）。服务端 `TalkBudget` 只节流 **NPC 自主发言路径**（`minReplyIntervalMs` / `maxMessagesPerNpcPerHour` / `maxNpcCallsPerTick`）；**玩家发信端不受 `minReplyIntervalMs` 约束**——每条消息只做审核并触发一轮后台波次，NPC 调用由 `maxNpcCallsPerTick` 兜底。因此连续点发不会被服务端按间隔拦截，**前端必须对发送按钮做防抖**；这不是绕过额度——微信不是一次「世界行动」，也不写 canon/permanent，只产生 `msg.sent` 私有事件和私忆。

- `actorId` 必须用建房时服务端签发的 `plr_xxx`，**前端不得自己拼或猜**。
- 所有写请求仍走现有鉴权/房间 gate；`guardRoom` 会校验 actorId 是否属于该房间，越权返回 HTTP 200 `{ok:false, code:"E_UNAUTHORIZED"|...}`。
- `POST` 的 `from` 必须是当前玩家自己的 actorId。后端不替你填；填别人的 actorId 会被房间 gate 拒。

## 2. MessageDigest / MessageRecord 长什么样

```ts
interface MessageDigest {
  id: string;            // msg_room_... 事件投影出来的稳定 id
  from: string;          // 发送者 actorId
  kind: "gossip" | "reply" | "player" | "system";
  content: string;       // 只有正文，没有动作通道
  rootId?: string;       // 八卦链根 id（同一条八卦的多跳转发共享）
  createdAt: number;     // 服务端时间戳
}
```

`GET /messages` 返回给玩家的是**该 actorId 作为收件人的消息**。`POST` 成功后返回的 `gossip.message` 里，`message.to` 是目标 NPC；前端在"已发送"列表里自己按 `from === myActorId` 展示即可，服务端不会把它塞进别人的收件箱。

## 3. SSE 渲染规则

- 连接 `messages/stream?actorId=<myActorId>`；`event: gossip.message`，`data` 是完整 `GossipEvent`。
- **只渲染 `message.from === myActorId || message.to === myActorId` 的事件**；其余直接丢弃（服务端已过滤一遍，前端再做一次是纵深防御）。
- `gossip.committed` / `gossip.dropped` / `gossip.error` 不要当成消息气泡渲染；只用于调试面板或静默忽略。
- 断线重连：先 `GET /messages` 补历史，再订阅 SSE。不要只靠 SSE，否则断线期间的八卦会丢。
- SSE 事件里 `content` 是**不可信文本**，必须按纯文本渲染（转义），不要 `innerHTML`，不要把它当指令。

## 4. 四种群聊说话模式（现有能力，别和微信混了）

面对面群聊仍走 `POST /rooms/:id/turns`，`Utterance` 的四种模式由数据文件 `content/v2/utterance-modes.json` 定义：

| 模式 | 目标看到的通道 | 其他人（含玩家）看到的通道 |
|---|---|---|
| `broadcast` | content + action | content + action |
| `addressed` | content + action + "对 X 说" notice | content + action + notice |
| `whisper` | **只有 content**（无悄悄话标记） | 只有 coverAction（神色） |
| `signal` | 只有 action（眼神/手势） | 只有 coverAction（无意义小动作） |

新增 `dm` 模式：目标可不在场，`targetPresence:"any"`、`visibility:"private"`。它用于"群聊界面里给不在场 NPC 说一句"，底层仍走 `conversation`，不要和微信 `msg.send` 混为一谈。

**微信没有 action 通道**。玩家给 NPC 发消息走 `POST /messages`，NPC 之间传播走引擎后台 `GossipHost.step()`，前端只订阅结果。

## 5. 预算与节流（别在前端重复实现）

`TalkBudget` 在服务端、在**调用 LLM 之前**生效：最短回信间隔、每 NPC 每小时条数、每波次调用上限。前端不要：

- 自己用 `setTimeout` 假设 NPC 多久会回；回复时间由服务端预算决定，可能不回。
- 连点发送按钮刷屏：后端会按预算丢弃，前端应做 1~2 秒的 UI 防抖，并把 `ok:false` 的 code 显示成友好提示。
- 显示"对方正在输入"这类状态：引擎没有这个事件，做出来就是假状态。

## 6. 玩家离线时的正确预期

- 玩家不在房间/不在页面时， NPC 之间仍会按后台波次互发微信并传播八卦。
- 玩家重新打开页面后，`GET /messages` 会看到自己作为收件人错过的消息；自己发出去的消息在"已发送"里（用 `POST` 返回值或本地记录）。
- 玩家不是收发任一方时，**那些消息永远不可见**。不要试图从 `/events` 里翻 `msg.sent`——`Envelope.audience` 在 Transport 前已过滤，且 SSE 层也不推给非参与方。

## 7. 已知未接线 / 不要假设存在的东西

- 前端收件箱 UI、@ 选择器、模式切换、插话按钮：需要你们实现；后端接口已就绪。
- `msg.read` 已读回执：**未实现**，不要设计依赖它的交互。
- 微信的"神色/动作"：**不存在**，不要设计占位文案。
- `conversation.notice` 不用于微信；不要监听它来显示私信提示。
- 会话、预算计数目前是**进程内内存**：重启后清空，前端不要把它们当持久数据。

## 8. 联调自检清单

1. 建房 → 用返回的 actorId 连 `messages/stream`。
2. `POST /messages` 给在场/不在场 NPC 各发一条，都应返回 `ok:true`。
3. NPC 回复经 SSE 到达，且只出现自己收发双方的 `gossip.message`。
4. 用另一个玩家账号订阅同一房间，确认看不到上述私信。
5. 快速连发 20 条，确认后端按预算丢弃时前端不崩、有明确提示。
6. 刷新页面后先 `GET /messages` 再订阅 SSE，历史不丢。

有任何字段缺失/语义不符，先在 `dev/v2` 开 issue，别在前端做兼容分支——兼容分支会把契约漂移藏起来。
