## 0. TL;DR

1. **三条不变量**（违反任一条，兼容性立刻崩塌）：
   - **I1 唯一写入口**：只有 `Arbiter.apply` 能改世界状态。模块、导演、UI、记忆都只产出 `Proposal[]`。
   - **I2 状态无硬编码字段**：实体状态是 `attrs: Record<string, value>`，键由 `registry/attrs.json` 声明。引擎代码里**不允许出现任何具体属性名**（如 `stamina`）。
   - **I3 新玩法 = 新数据 + 新目录**：模块只通过 `manifest.json` + 声明式能力接入，引擎按名字分发。加模块不改引擎。
2. **13 个 op 原语**（`attr.delta` / `attr.set` / `entity.create` / `entity.update` / `entity.tombstone` / `link.create` / `link.remove` / `move.to` / `time.advance` / `scene.set` / `memory.write` / `plot.upsert` / `msg.send`（dev/v2））构成闭集指令集。交易、学习、社交、密谋全部由它们组合——这是"引擎不用改"的形式化保证。
3. **世界状态 = 事件日志的投影**（event-sourced）。这一条同时解决：存档/回放、联机同步、NPC 离线推演、反作弊、调试。**做联机的成本从"重写"降到"加一个 Transport 实现"**。
4. **联机不是后加功能，是从第一天就遵守的纪律**：所有接口带 `roomId + actorId`，所有状态按房间隔离，所有流式消息带 `seq` 可续传。单人模式 = 只有 1 个 actor 的房间。
5. **NPC 自主多 agent 对话 = 一个接口 + 多个导演实现**。`Dialogue.open/step/interject/close` 是唯一入口；密谋、闲聊、课堂争论、玩家插入都只是不同 `DialogueDirector`。新增一种对话形态 = 加一个导演文件。
6. **AI 可以自由增减设定与 NPC 的边界**：`canon`（人工锁定，AI 只读）+ `soft`（AI 可创建/更新/软删）+ `x.*` 自由属性区。AI 产物默认 `canon=false`，通过 `canonize` 才能转正。

## 1. 相对 v1 的 8 处结构性调整

| # | v1 的做法 | 问题（面对"多人接手 + 联机 + AI 自由生成"） | v2 |
|---|---|---|---|
| ① | `PlayerState` / `NpcState` 是固定 TS 接口 | 加一个属性（如"压力值"）就要改引擎 + 改前端 + 改存档迁移 | `Entity.attrs` 动态 + `registry/attrs.json` 声明，UI 也读 registry |
| ② | 模块接口 8 个方法无版本、无能力声明 | 别人写的模块你不知道它要什么，冲突只能运行时炸 | `manifest.capabilities` 显式声明 + 启动期校验 + `apiVersion` |
| ③ | 状态直接存表（SQLite 行） | 联机要增量同步、断线要补发、回放要对齐 | 事件日志（append-only）+ 周期快照；表结构由投影生成 |
| ④ | 单玩家假设散落各处 | 加联机要全库改 `playerId` → 实际是重写 | **房间**是隔离单位；`actorId` 从第一天就是参数 |
| ⑤ | 密谋是硬编码的 `PlotDirector` | 想加"NPC 白天闲聊"就要再写一套调度 | 统一 `Dialogue` 接口 + `directorId` 选择实现 |
| ⑥ | NPC 与设定来自静态 JSON | 用户要"AI 自由增减" → 静态内容不够 | `canon` / `soft` 分层 + `entity.create` 由 AI 提议、Arbiter 校验 |
| ⑦ | 模块可能直接调 LLM | 密钥、成本、格式校验失控 | 模块**禁止**持有 LLM 客户端；只能通过 `ctx.llm`（受引擎管控、可 mock） |
| ⑧ | 文档是散文，接口靠"看代码" | 别人（和他的 AI）没法照着写 | 接口总表 + 模块规范 + AGENTS.md + **三个验收 demo** |

## 2. "只加变量/数据名，不改引擎"凭什么成立

这是本方案的核心命题，必须有机制支撑，否则是口号。四个机制：

### 2.1 属性注册表（Registry）—— 加变量只改 JSON

```jsonc
// content/registry/attrs.json（示意）
{
  "attrs": [
    { "key": "stamina",   "type": "number",  "scope": ["plr","npc"], "min": 0, "max": 100, "default": 80,
      "visibility": "public", "display": { "label": "体力", "order": 10, "style": "bar" } },
    { "key": "money",     "type": "number",  "scope": ["plr"],       "min": 0, "max": 99999, "default": 20,
      "visibility": "self",  "display": { "label": "零钱", "order": 20, "unit": "元" } },
    { "key": "guard",     "type": "number",  "scope": ["npc"],       "min": 0, "max": 100, "default": 0,
      "visibility": "secret" },                       // secret：不进 UI、不进叙事，只影响表现
    { "key": "mood",      "type": "enum",    "scope": ["npc"],       "values": ["calm","tense","angry"] }
  ]
}
```

- 引擎读 registry 校验；**代码里没有任何一处写死 `stamina`**。
- 前端数值面板由 `/api/v1/registry` 驱动渲染（`display.order/label/style`），新增属性不用改前端。
- 加"压力值"的完整成本：**在 JSON 里加 1 条 + 在玩模块里产出 `attr.delta`**。零行引擎代码。

### 2.2 13 个 op 原语的闭集 —— 新玩法 = 老原语的新组合

- 交易 = `attr.delta(money, -6)` + `link.create(holds, item_bread)` + `attr.delta(stamina, +5)`
- 学习 = `attr.delta(intellect, +2)` + `entity.create(lore_exam_topic)` + `plot.upsert`
- 密谋 = `plot.upsert` + `attr.delta(guard, +15)` + `memory.write`
- **想不出用 13 个原语表达的新玩法，通常意味着需求本身有问题**，而不是引擎缺功能。
- 真需要新原语 → 走 §0.4 的 `apiVersion` 流程（明确标为"破坏性、需全员回归"）。

### 2.3 能力注册表 + 数据注册 —— 加模块只加目录

模块通过 `manifest.json` 声明：`intents`（快路径）、`tools`（LLM 可调）、`triggers`（事件订阅）、`views`（UI 块）、`contentFiles`。引擎启动时扫描、校验、按名分发。**引擎不知道"交易"这个词的存在**。

### 2.4 事件日志 —— 加联机/加复盘不改业务代码

所有变化是 `Envelope[]`。联机 = 把 `Envelope` 广播出去；存档 = 存快照 + 事件；复盘 = 重放；NPC 离线推演 = 在后台对同一日志跑导演。

> **自检口诀**：如果你发现自己在引擎里写 `if (moduleId === "trade")`，说明设计跑偏了——应该改成能力查询。

## 3. 扩展点矩阵（谁改什么）

| 想做的事 | 要改的地方 | 动引擎？ | 动前端？ |
|---|---|---|---|
| 新增一个属性（体力/好感/压力） | `registry/attrs.json` + 玩法里发 `attr.delta` | ❌ | ❌ |
| 新增一个 NPC | `content/npcs/*.json`（或 AI 运行时创建） | ❌ | ❌ |
| 新增一个地点 | `content/world/locations.json` + 邻接 | ❌ | ❌ |
| 新增一件物品 | `content/items/*.json` | ❌ | ❌ |
| 新增玩法模块（交易/学习/社团） | 新目录 `content/modules/<id>/` + manifest + index 一行 | ❌ | 一般 ❌ |
| 新增 LLM 工具 | manifest `tools` + handler | ❌ | ❌ |
| 新增事件类型 | `registry/events.json` 一条 | ❌ | 按需订阅 |
| 新增 UI 弹窗 | 模块 `views` + `view` 方法 | ❌ | ❌（宿主渲染） |
| 新增一种 NPC 对话形态 | `content/directors/<id>.ts` 一个文件 | ❌ | ❌ |
| 新增一个房间模式（合作/PvP/旁观） | `room.mode` 枚举 + 策略实现 | ⚠️ 小改 | ❌ |
| 新增一个 op 原语 | 契约 + Arbiter | ✅ | 视情况 |
| 改裁决规则（如上限算法） | Arbiter | ✅ | ❌ |

**这张表就是交接文档的骨架**：接手的人只需要前 9 行，永远不需要第 11、12 行。

## 4. 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│ 表现层 apps/web（React + Vite）：纯渲染 View，不含规则        │
└───────────────▲──────────────────────────┬───────────────────┘
                │ View / Envelope(SSE)     │ 玩家输入
┌───────────────┴──────────────────────────▼───────────────────┐
│ 传输层 Transport（HTTP+SSE 现在 / WS 以后，接口同构）          │
└───────────────▲──────────────────────────┬───────────────────┘
                │                          │
┌───────────────┴──────────────────────────▼───────────────────┐
│ 编排层 Orchestrator                                          │
│  Turn（一次输入 → 一次回合）  Dialogue（NPC 会话）  Tick（时间）│
└───────▲──────────────▲──────────────▲──────────────▲─────────┘
        │              │              │              │
   ┌────┴────┐   ┌─────┴─────┐  ┌─────┴─────┐  ┌─────┴─────┐
   │ Modules │   │ Directors │  │  Memory   │  │    LLM    │
   │(插件)   │   │ (对话导演) │  │ (检索/压缩)│  │ (网关)    │
   └────┬────┘   └─────┬─────┘  └─────┬─────┘  └───────────┘
        └──────────────┴──────────────┘
                       │ Proposal[]（只有提议权）
              ┌────────▼─────────┐
              │   Arbiter（裁决） │ ← 唯一写入口（I1）
              └────────┬─────────┘
                       │ Envelope[]
              ┌────────▼─────────┐
              │ EventLog+Snapshot │  世界状态的唯一真相
              └────────┬─────────┘
                       │ 投影
              ┌────────▼─────────┐
              │ Registry (数据)   │  attrs/events/intents/tools 声明
              └──────────────────┘
```

**读法**：上层只能往下调用；`Proposal` 向上回流到 Arbiter；任何跨层直接写库都是违规。

## 6. 四个"层"的职责（避免概念混淆）

| 层 | 是什么 | 谁写 | 能否直接改状态 | 例子 |
|---|---|---|---|---|
| **Data**（`content/`） | 属性、实体、模块配置、提示词 | 内容作者 / AI 推演 | — | `attrs.json`、`npcs/zhangsan.json` |
| **Module**（`content/modules/<id>`） | 确定性的规则运算（价格、成绩、概率） | 其他开发者 | ❌ 只出 `Proposal` | `trade.buy` |
| **Director**（`content/directors/<id>`） | 对话/剧情的生成策略 | 你或资深成员 | ❌ 只出 `Proposal` | `npc.plot` |
| **Engine**（`packages/engine`） | 校验、裁决、调度、存储、传输 | **你** | ✅ 唯一入口 | `Arbiter.apply` |

> 一句话区分：**Module 算数，Director 说话，Engine 记账**。

## 7. 内容分层：canon / soft / x 区

用户要求"除世界观和重要客观事实外，其他设定和 NPC 都能由 AI 推演自由增减"。落成三档：

| 档 | 存哪 | AI 可否创建 | AI 可否修改 | 可否删除 | 例子 |
|---|---|---|---|---|---|
| **canon** | `content/canon/`，运行时只读（加载进 registry） | ❌ | ❌（只能引用） | ❌ | 学校名、三条校规、主角转学生身份、李教授是班主任 |
| **soft** | DB 实体，`canon=false` | ✅ 通过 `entity.create` | ✅ 白名单字段 | ✅ 软删（tombstone） | 新同学、传闻、小卖部新品、临时地点 |
| **x 区** | 实体 `attrs["x.*"]` | ✅ 直接写 | ✅ | ✅ 随实体 | "他今晚看起来怪怪的"这类氛围标记 |

**AI 创建实体的约束**（`entity.create` 的校验规则，由 Arbiter 统一执行）：
- `origin` 自动标 `"ai"`，`canon` 强制 `false`；
- 数量上限：每房间 soft NPC ≤ 24、地点 ≤ 40、物品 ≤ 200（超限拒绝，`E_OVER_LIMIT`）；
- 命名空间校验：id 不得与 canon 冲突；`name` 不得与 canon 实体同名（防"另一个张三"）；
- 不得创建 `kind=fact`（事实只能人工）；
- 不得 `entity.update` canon 实体的 `name/identity/attrs` 白名单外字段（`E_CANON_LOCKED`）；
- 每次创建都记 `fabricatedBy`（哪回合、哪个导演），可审计、可一键回滚某夜的 AI 产物。

详见 `05-内容边界与AI推演.md`。

## 8. 联机兼容：现在必须遵守的 6 条纪律

> 不实现联机，但违反这 6 条，将来就要重写。每条都便宜，现在做几乎零成本。

| # | 纪律 | 现在的做法 | 违反后果 |
|---|---|---|---|
| 1 | **房间隔离** | 所有状态查询/写入都带 `roomId`；`WorldState` 挂 room | 全局单例状态，多人必串 |
| 2 | **actorId 显式** | 每个动作/消息都带发起者；玩家不叫 `player`，叫 `plr_xxx` | 到处 `currentPlayer` 全局变量 |
| 3 | **seq 单调 + 可续传** | 每条 `Envelope` 有 `seq`；SSE 支持 `Last-Event-ID` | 断线只能刷新重开 |
| 4 | **回合幂等** | `clientTurnId` 去重，重复提交返回同一结果 | 网络重试导致扣两次钱 |
| 5 | **不做隐藏的本地状态** | 前端不缓存权威状态，只渲染服务端 `View` | 两人看到不同的世界 |
| 6 | **时间由服务端推** | `clock.advanced` 是事件，不是前端计时器 | 各端时间不同步 |

**联机时的回合冲突策略**（预留，不在 M0–M5 实现）：房间模式 `coop` 用"轮流 + 插话窗口"；`pvp` 用"同时提交、按序裁决"。接口上表现为 `Turn.run` 接受 `options.order`，引擎不需要为两种模式写两套代码。

详见 `04-联机与多Agent.md`。

## 9. NPC 自主多 agent 对话：一个接口，N 个导演

**问题**：如果"密谋"是硬编码的一个类，将来要加"NPC 课间闲聊""三个 NPC 争论谁该背锅""玩家插话打断密谋"，每次都要动引擎。

**方案**：会话骨架（引擎负责）+ 导演（插件负责）。

```
引擎 Dialogue 骨架负责：
  · 参与者是谁、谁在场、谁能知道什么（信息边界）
  · 发言顺序、轮数上限、何时结束
  · 每轮产出写进各自记忆（视角化：同一件事两份不同叙述）
  · 守卫值/关系等 Proposal 的产出与裁决
  · 玩家中途插话（interject）的处理

导演 DialogueDirector 负责：
  · 这一轮说些什么（prompt、情绪、是否施压）
  · 是否值得继续（提前结束）
  · 产出哪些 Proposal
```

内置导演：`npc.plot`（夜间密谋）、`npc.smalltalk`（低频闲聊）、`npc.react`（事件反应）、`npc.player`（玩家多人对话）、`npc.debate`（课堂讨论）。

**这直接满足"NPC 自主多 agent 对话的接口"**：单人时是后台 tick 触发密谋；联机时是同一套接口 + 广播；将来"NPC 之间持续自治"也只是把 `npc.smalltalk` 的触发频率调高——不动引擎。

**成本控制（不影响兼容性）**：导演可以在 manifest 里声明 `budget`，引擎按"每房间每小时 LLM 调用上限"统一节流。

## 10. 里程碑（v2，兼职节奏）

## 11. 明确不做（防止过度设计）

| 不做 | 理由 |
|---|---|
| 运行时热插拔模块 | 收益低（改模块本来就要重启），风险高（状态不一致） |
| 模块沙箱隔离（vm/worker） | 你自己信任的人写模块，不需要；崩溃隔离用 try/catch 即可 |
| 通用 ECS 框架 / 自研脚本语言 | 会变成"造引擎的引擎"，拖延期 |
| 微服务 / 消息队列 | 单进程 + SQLite 足够扛到几十人同房 |
| 向量数据库 | 先用结构化检索（v1 §5 已验证够用），触发条件写在 v1 §5.6 |
| 客户端预测 / 权威回滚 | 文字回合制不需要 |
| 完整权限系统 | MVP 用邀请码 + 房间 owner |
| 支持非 LLM 的纯规则玩法 | 可以，但走 `skipLLM` 的模块即可，不做第二套引擎 |

## 12. 验收：三个"不改引擎"的演示

这三条是你交付给团队的**可靠性证明**，写进 README：

1. **加变量**：在 `content/registry/attrs.json` 加 `stress`（压力），重启 → 玩家面板自动出现"压力"，无需改前端/引擎。
2. **加模块**：新建 `content/modules/library/`（借书、逾期罚款），重启 → 玩家在图书馆能"借书"，LLM 能调用 `library.borrow`，不改 `packages/engine` 任何文件。
3. **加对话形态**：新建 `content/directors/npc.rumor.ts`（三人传闲话），在 manifest 声明，触发时只改 `directorId`，不改 `packages/engine`。

**加分项**：开第二个浏览器窗口进同一房间（`room.mode=coop`），检查两个窗口的现象是否一致。

## 13. 风险（v2 新增的）

| 风险 | 表现 | 对策 |
|---|---|---|
| **过度抽象** | 为了"通用"设计了没人用的能力（视图 DSL、模块 DSL） | 每个扩展点必须有**至少一个真实使用者**才允许存在；M2 只做 trade 一个模块 |
| **注册表失控** | 属性膨胀到 80 个，prompt 里全塞 | registry 加 `promptBudget` 分组，只注入 `core` 组；其余按模块需求注入 |
| **AI 生成污染** | 一晚生成 15 个 NPC，剧情崩 | §7 的数量上限 + 人审 `canonize` + 每夜产物可一键回滚 |
| **导演失控** | 某导演每晚 40 次调用 | 每房间每小时调用配额（`dialogue.budget`），超了降级为 `npc.smalltalk` 简版 |
| **事件日志膨胀** | SQLite 几十万条，检索慢 | 周期快照（每 200 回合）+ 归档冷表；单房间日志上限 5 万条后强制快照 |
| **契约漂移** | 别人按旧文档写，名字对不上 | `check-contract` 进 CI；本文档是唯一名字来源；`apiVersion` 不匹配拒绝加载 |
